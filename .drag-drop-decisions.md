# Drag & Drop primitive — design decisions

Scoping and design decisions for the new headless Angular drag-and-drop
primitive, resolved in a stress-test/grill session against the feature survey
in [`.drag-drop-features.md`](./.drag-drop-features.md). That file is the
"what's possible"; this file is the "what we're building and in what order".

Section references (§n) point at `.drag-drop-features.md`.

## Foundation

- **Engine: Pointer Events only** (mouse / touch / pen unified, plus keyboard).
  No native HTML5 DnD backend. Consequence: OS / file / cross-window drag (§16)
  is permanently out of scope for this primitive - not a v1 cut, a design
  boundary. Rationale: full control, mobile + keyboard parity, custom previews,
  and no ~13-browser-bug normalization burden (§1).
- **Architecture: Angular-native `createPrimitive` / `-state.ts` factories.**
  No framework-agnostic core. ng-primitives is Angular-only, so dnd-kit's
  neutral-core + adapters layer is YAGNI here - one framework, one binding.
  Drag math lives in signal-based state factories like every other primitive
  (§21).
- **Parts (CDK-style decomposition):**
  - `ngpDrag` - the draggable item.
  - `ngpDropList` - the container; reordering (sortable) is a mode of the list,
    not a separate concept.
  - `ngpDragHandle` - optional handle sub-element.
  - Preview / placeholder / insertion-line are **template slots** on the list/
    item, not separate primitives.

  Rationale: fewest concepts, familiar to Angular devs coming from CDK. A
  standalone `ngpDroppable` (drop zone that isn't a list, §5) can come later if
  demand appears.

## Behaviour

- **Data flow: two-way bindable order AND a drop event.** Uncontrolled path:
  bind `[(...)]` and the list reorders internally, emitting the change.
  Controlled path: bind one-way and own the mutation via the drop event. Matches
  the `controlledState` idiom used across ng-primitives. **The two-way value
  commits on _drop_, not continuously** - mid-drag the DOM shifts visually
  (transforms) but the bound array is untouched until the drop lands (§18).
- **Measurement spine: arithmetic index + known/estimated item size.** Positions
  are computed from index + size, not measured from all mounted rects. Built
  this way from Milestone 1 to avoid a later rewrite. This is what makes true
  windowing possible (§2, §15). Trade-off accepted: a size contract on the
  consumer (a size input, or a virtual-scroll adapter supplies it).
- **Collision: pluggable collision function from day one.** Not hard-coded
  list-slot detection. Generality chosen up front so grids / free drop zones
  slot in without an API break (§8). **Contract note:** the collision function
  operates on **computed rects**, never live DOM rects - see the tension at the
  bottom.
- **Accessibility (non-negotiable, Milestone 1):**
  - **Position-based keyboard model** (React Aria style, right for lists):
    Enter/Space picks up; arrows move to the next/prev **slot** (discrete
    positions, not pixel nudges); Tab moves between connected lists; Enter
    drops; Escape cancels and restores (§13).
  - **Live-region announcements:** the primitive renders the off-screen live
    region and ships **English, position-based** default copy ("Picked up X,
    position 2 of 5"), every message overridable. No built-in i18n / 30+
    languages - that maintenance surface is out of scope; consumers localize
    (§13).
  - **Public move operations** - `moveToIndex` / `moveToList` / `moveUp` /
    `moveDown` on the item/list state - so consumers can wire the Atlassian
    "Move to…" action-menu pattern (which user-testing found beats keyboard
    drag) to their own `ngpMenu`. We enable the pattern; we don't own menu UI.
    Also useful for testing.
- **Drag preview: detached overlay in a portal**, decoupled from the source
  element (dnd-kit `DragOverlay` model). The source item can recycle / unmount
  mid-drag under windowing, so the preview cannot be the source element.
  Consumer supplies the preview template; default is a clone (§6, §15).
- **Drop indicator: both** a templated placeholder node **and** a computed
  insertion line (Atlassian 2px spec, §7). The gap opens arithmetically at the
  target index (positions are known, so it animates cleanly); the insertion
  line is an optional consumer-templated slot.
- **Reorder animation: CSS transform transition.** Because positions are
  computed (not FLIP-measured), the sibling shift is a plain transform
  transition. Expose `duration` + `easing` inputs (dnd-kit default
  `{ 200ms, ease }`); collapse to 0 under `prefers-reduced-motion`. No spring
  runtime - springs are the consumer's job (§14).

## Research-settled defaults (adopted without further debate)

These are taken directly from the survey's verified findings; no separate
decision needed.

- **Multi-list (§3):** CDK model - connect by id or reference, auto-connect via
  a group wrapper, `transfer` / `copy` helpers on drop, plus enter/sort
  predicates as the data-agnostic validation hooks.
- **Constraints (§11):** CDK set - axis lock, boundary containment, drag handle,
  start-delay / hold-to-drag, disabled item/list.
- **Auto-scroll (§9):** dnd-kit `Options` shape - `threshold` as a 0-1 fraction
  per axis (`0` disables that axis), an `acceleration` speed multiplier, a
  `canScroll` predicate, innermost-eligible-ancestor selection for nested
  scrollers. **Trigger on the draggable _center_** (rbd's approach), not just the
  pointer, so keyboard drags scroll too. Eased (not linear) speed curve.

## Relationship to the existing `tree` primitive

The `tree` primitive already ships its own hand-rolled DnD (`tree-drag-preview`,
`tree-node-drag-handle`, dedicated DnD tests). Decision: **the generic primitive
stands alone; the tree is left unchanged.** Nested / reparent / auto-expand
behaviour (§10) is therefore not this primitive's responsibility in v1. The
duplication is logged as future tech-debt to reconcile - once the generic
primitive is proven, the tree's DnD can migrate to compose it (the ng-primitives
state-composition ethos), but not as part of this effort and not at the risk of
regressing a shipped feature.

## Delivery — sequenced, not one big v1

The full set of decisions above is larger than what Angular CDK ships. Rather
than build it all before releasing, it lands as a sequence, each milestone
proven before the next compounds onto it. Same destination, safer path.

- **M1 — prove the core.** Sortable, multi-list connect/transfer, full a11y
  (keyboard + announcements + move ops), detached overlay preview, indicators,
  transition animation, constraints, and auto-scroll. Built **on the arithmetic
  measurement spine** so there's no rewrite when windowing arrives - but no
  windowed rendering yet.
- **M2 — windowing.** A small virtual-scroll **adapter contract** (item count,
  size-for-index, rendered range) with a `CdkVirtualScrollViewport` adapter as
  the first implementation. Decouples the primitive from any one virtualizer.
- **M3 — multi-select drag (§17).** Selection input, stacked-count preview,
  batch move operations (the move ops from M1 already take index arrays where
  it's cheap to do so).
- **M4 — pluggable-collision generality.** Fully exercise the collision function
  over grids / arbitrary drop zones (§4, §5).

## The one tension to hold

**Pluggable collision (day one) × arithmetic known-size measurement.** Pluggable
collision naturally wants measured rects of real droppables; the arithmetic
spine wants computed positions from index + size. In M1 they coexist fine
(collision over a fully-mounted list). They only collide at M2/M4: a custom
collision function over a **windowed** list cannot measure unmounted targets.

**Mitigation, decided now:** write the collision-function contract to receive
**computed rects** (from the measurement spine), never live DOM rects. Do this
from M1. That single constraint is what keeps M4 from forcing an M1 rewrite.
